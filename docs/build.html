Build log

Each milestone in the order it was built: the goal, the approach, how I checked it, and what it taught me. Dates come from the commit history.

1 · Schema exploration and camera sync Done

Sep 11 – Sep 13, 2026 · notebook

nuScenes devkit Pandas Matplotlib

Goal. Understand what nuScenes actually contains, and how its tables relate, before deciding what to extract.

Approach. Worked through the devkit tutorial on v1.0-mini (scenes, samples, sample_data, calibrated sensors, ego pose, annotations, instances, categories), then added my own extraction on top: walk each scene's samples, pull every sensor's data with its calibration, and measure each camera's timestamp skew against the sample's keyframe.

How I checked it. Thresholded skew at 43.5 ms and plotted it three ways (a histogram, a per-sample scatter with the threshold line, and a per-camera box plot) to see whether misalignment was rare noise or one camera being systematically late.

What I learned. A nuScenes "sample" is a keyframe, not a moment where every sensor fired together: each camera's frame is the nearest one to the keyframe, so "synced" always means "synced within some tolerance", and that tolerance is a choice worth measuring before building on it.

2 · Ingestion module and Parquet tables Done

Sep 13 – Nov 1, 2026 · checks

PyArrow Schema design

Goal. Turn the notebook's extraction into a module that writes typed Parquet tables (samples, sensor data, annotations, projected 2D boxes).

Approach. Moved the logic out of the notebook, then replaced every literal table/field name with a shared key vocabulary (nuscenes.py, ingestion_keys.py) so ingestion, transform and table-building all read the same names. Row builders flatten each sample's aggregate record into rows validated against explicit pyarrow schemas.

How I checked it. Three scripts, each against something independent of the code under test: sample traversal against nuScenes' own table scan, every ingested field against the raw devkit record (64,192 values), and every table row against the schema plus a small re-indexer written separately from the row builders (136,616 values).

What broke. Running the checks found real bugs: a key renamed in one place but not its callers (it crashed verify_ingestion_keys.py), schema literals that weren't valid pyarrow schemas, annotation rows built from the wrong column map, and a call to a function that didn't exist. All were fixed in one pass, and the checks have passed since.

What I learned. The bugs that matter in data plumbing are wiring bugs: the right logic fed the wrong record. They look fine until something independent reads the same source. That's why the table check uses its own re-indexer rather than the code it's checking: reusing it would have hidden exactly these bugs.

3 · Projection: global → ego → camera → pixel Done

Sep 24 – Nov 1, 2026 · checks · analysis

SE(3) / SciPy Computer vision

Goal. Project every annotated 3D box into each camera that sees it, and prove the projection is right.

Approach. An SE(3) chain built on scipy's RigidTransform: box corners from global to ego to camera frame, an in-front-of-camera filter, the intrinsics and perspective divide, then clipping the projected hull to the image canvas.

How I checked it. nuScenes ships a script that does the same projection, but it only outputs final boxes, so I forked it to also output the corners after every intermediate stage, and diffed my pipeline against it stage by stage. A disagreement now points at the exact transform that caused it. Then the end result: 17,683 boxes, lowest IoU 0.9997, with 0 boxes missing and 0 invented.

What I learned. "Matches the reference" is only as strong as the reference: this proves my code agrees with the devkit's implementation, not with an independent ground truth (nuScenes has no separately annotated 2D boxes). And where IoU dips at all, it's on tiny or edge-clipped boxes, where a sub-pixel difference is a large fraction of the box. That's why the minimum-area cutoff for the image gallery is a setting (config.toml), not a constant.

4 · Ray-parallelized ingestion Done

Oct 9 – Nov 1, 2026 · benchmark

Ray Performance benchmarking

Goal. Find out whether parallelizing ingestion actually helps, and by how much.

Approach. A Ray driver (partition.py) that batches scenes, resolves each batch into a plain-dict manifest in the driver (nusc.get() is cheap list indexing, since NuScenes.__init__ already loads every table eagerly), ray.put()s that manifest once per batch, and farms it out to two independent table-writing tasks per batch, with per-task timing (queue wait, compute, disk write). A benchmark harness reruns it at 1/2/4/8 workers with repeated timed runs and records whole-machine CPU utilization.

Result. The best run was 1.53× faster than one worker, at 4 workers; 8 workers was slower than 4. At 4 workers, 58% of each run is fixed startup cost (interpreter, imports, ray.init(), loading the devkit's tables), which no number of workers can shrink.

What I learned.

  • On a dataset this small, parallelism is capped by its fixed costs before it is capped by cores. I also caught a misleading chart of my own: a numeric worker-count axis invented an intermediate tick ("6") with no run behind it. Worker counts are sweep values, not a continuous range, so the axis is now categorical.
  • A Ray task is a separate process, not a thread. Nothing in the driver (not even an already-loaded nusc) is visible inside a task; only what's explicitly passed in exists on the worker side. That one fact ruled out most of the designs I tried first: shipping nusc itself to every worker, a global buffer a second task could read from, a single nusc shared across per-sample tasks. The manifest pattern (resolve everything to a plain dict in the driver, hand that to the tasks) exists because of it.
  • Not every independent step deserves its own task. I started with one task per output table (three for the core tables, one for the projected bboxes), since each write is genuinely independent of the others. Writing a table is cheap reshaping, though, so splitting the three core writes further only paid scheduling and deserialization overhead per task without adding real parallel compute. Consolidating them into one task, alongside the bbox task, is why there are two tasks per batch, not four.

5 · Geometric BEV fusion Done

Nov 1 – Nov 4, 2026 · checks · interactive views

OpenCV Plotly 3D geometry

Goal. Fuse LiDAR and cameras into one top-down view: every LiDAR point, coloured by the camera that sees it, with annotated boxes overlaid.

Approach. Load each sample's LiDAR sweep into the ego frame; project the points into every camera with the already-validated projection chain and sample each point's colour (bilinear, via cv2.remap); bring the annotation boxes into the same frame; then render as a scatter, a multi-channel raster (colour, height, intensity), and 3D views.

How I checked it. Six checks, again each against something independent. The strongest is that the number of my LiDAR points inside each annotated box matches nuScenes' own num_lidar_pts for 205 / 205 boxes. The others check the ego-frame axes against how the car actually moved, the LiDAR file's columns against the devkit's loader, colour sampling against hand-computed interpolation, and the raster against a deliberately naive reimplementation.

What I learned.

  • Rendering libraries have opinions. Plotly's image trace draws row 0 at the top, the opposite of this project's forward-is-up convention. That would have silently flipped the whole view front-to-back; I only trusted the fix after rendering both variants and looking.
  • Averaging is a modelling decision. Several LiDAR points can land in one raster cell at different heights (a branch over a road), so each cell keeps the surface nearest the sensor rather than blending unrelated ones. Exact ties are averaged: on real data they turned out to be multiple returns from one spot, not different surfaces.
  • Colour is a constraint, not decoration. With up to ten categories on screen, no colour-blind-safe palette held up past seven distinct colours, so the six most common categories get their own colour and the rest share one.
